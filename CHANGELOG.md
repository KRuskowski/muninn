# Changelog

All notable changes to muninn are recorded here, written for people who use muninn rather than people who read its source.

## Unreleased

- Project started, under the MIT license.
- The foundation is in place: a shared file format with corruption detection, exact (brute-force) vector search with cosine, dot-product and Euclidean similarity, and filtering of results by document.
- Exact vector search is much faster: it uses every CPU core and applies filters while it searches, so a filtered search costs no more than an unfiltered one.
- Fast approximate vector search (HNSW) for large collections. It builds on all CPU cores, accepts new vectors at any time (also after being reopened from disk), and on our test data finds 99% or more of the true ten nearest neighbours at its default settings.
- Filtered vector search always returns as many results as you asked for whenever that many documents match the filter, and picks the fastest way to do it automatically, including when only a handful of documents match.
- Optional vector compression (one byte or one bit per dimension) to search with less memory traffic; the best candidates are re-checked against the original vectors, so accuracy stays high.
- Vector indexes are saved as a single file and open instantly, however large they are: nothing has to be read into memory up front.
- Vector indexes are more robust: adding vectors to an index opened from a damaged file no longer crashes, an empty compressed index can be saved and reopened, asking for an extremely large number of results no longer exhausts memory, and a failed insert leaves the index exactly as it was.
- Every vector added to an approximate (HNSW) index can be found again: previously a few vectors per tens of thousands could become unreachable during a build, more often when building on many CPU cores, so searching for them returned other vectors instead.
- Vector comparisons are now several times faster on modern Intel, AMD and ARM processors: muninn automatically uses the fastest instructions your processor offers, with no setup. Vectors can also be compared in half precision, which halves the memory they need. Setting `MUNINN_ISA=scalar` (or `avx2`, `avx512`, `neon`) limits which processor features are used, for troubleshooting and comparisons.
- Full-text search: documents can be searched by keywords and ranked by relevance (BM25, the standard used by Elasticsearch and Lucene). A document matches if it contains any of the query words; documents containing rarer words, more often, in shorter text rank higher.
- Text is matched regardless of upper/lower case and works for any language that separates words with spaces, including accented and non-Latin scripts. Optionally, accents can be ignored ("café" finds "cafe"), common English words such as "the" and "and" can be skipped, and English word endings can be ignored ("running" finds "run"). The chosen settings are saved with the index, so searches always treat text the same way it was indexed.
- Newly added text is searchable immediately, and search stays fast as collections grow: only the documents that can still make the top results are examined, yet the results are exactly the same as checking every document.
- Search filters (for example "only documents from this user") are applied while searching, so you always get the requested number of results when enough matching documents exist.
- Relevance scores stay consistent across a whole collection even when it is stored in several parts, so results from different parts can be combined fairly.
- Text indexes are stored compactly on disk (about 2 bytes per word in our tests), open instantly, and are checked for corruption. Indexes can be combined into one, with deleted documents removed.
- A search may contain up to 1024 different words; longer searches are refused with a clear error. Repeating a word does not count against the limit.
- Current limitation: languages written without spaces between words (Chinese, Japanese, Thai) are not yet split into words, so searching them only finds exact runs of text.
- Index files with damaged trailing bytes are now always rejected, and asking for an extremely large number of results no longer exhausts memory.
- Every change is recorded in a write-ahead log before it is confirmed. After a crash or power loss, muninn recovers every confirmed change; a change that was only half written when the machine went down is dropped cleanly instead of stopping the database from opening.
- You can choose how strictly writes are protected: confirmed only once they are on disk (safest), written to disk at a short fixed interval such as every 10 ms (faster; a power cut can lose at most that interval), or left to the operating system (fastest; survives the application crashing, not the machine). When many writers save at the same time they share disk flushes, so total write throughput grows with the number of writers.
- Documents can be identified by your own ids, either numbers or text.
- Stored documents (JSON) are read directly from the data files without loading or copying them first, so opening a large collection is quick.
- Saving the list of a collection's data files is all-or-nothing: a crash during a save leaves the previous state intact, and leftover temporary or obsolete files can be cleaned up safely.
- A data directory can be opened for writing by only one program at a time; a second attempt gets a clear "already open" error instead of risking damage to the data.

It measures both muninn's search indexes on their own and the complete database as an application uses it (adding documents durably, then searching). See `docs/BENCHMARKS.md`.

- muninn is now a database: open a data directory, create named collections, and store documents that combine a vector, any number of text fields and a JSON payload. Documents are identified by your own ids (numbers or text); writing a document with an existing id replaces it, and documents can be deleted.
- One search can ask for similar vectors, for matching words, or for both at once (hybrid search). Hybrid results are combined by rank (reciprocal-rank fusion, the default) or by a weighted blend of normalised scores that you choose. Results can include each document's stored payload, and a document can be fetched by id.
- Every batch of writes is all-or-nothing: searches never see half a batch, and after a crash a batch is either fully there or not at all. Confirmed writes survive crashes according to the durability setting you choose.
- New documents are searchable as soon as the write returns. Large collections are written to disk in the background while searching and writing continue, and the parts on disk are merged in the background so searches stay fast and deleted documents stop taking space. You can also trigger both yourself.
- Text relevance scores are the same however a collection happens to be split on disk, and documents with equal scores always come back in the order they were written.
- Searches can be limited to a list of document ids or by a test on the id, and filters can be combined with and, or and not. Filters are applied while searching, so you get as many results as you asked for whenever that many documents match.
- Background merging keeps the number of on-disk parts small even under a constant stream of deletes, and an explicit compaction is never held up indefinitely by ongoing writes.
- Search results can be filtered by document fields: exact matches on labels (for example "language is en"), a list of allowed values ("tag is a or b"), number ranges ("year 2020 or later", "price below 10"), whether a field is present at all, and any combination of these with and, or and not. Filters can also be written as JSON, for example `{"and":[{"eq":{"lang":"en"}},{"range":{"year":{"gte":2020}}}]}`, and a mistake in a filter is reported with the exact place it occurs.
- Each collection declares which document fields can be filtered and what kind of value they hold: a label, a whole number, a decimal number, or true/false. Fields inside nested objects are reached with a dotted name such as `meta.lang`. A field holding a list matches when any item in the list matches. A document whose field holds the wrong kind of value (for example text where a number is expected) is simply treated as not having that field, rather than causing an error. A collection can declare up to 4096 filterable fields.
- Newly added documents can be filtered on immediately. Filter data is stored compactly on disk (about 45 bytes per document with six filterable fields in our tests), opens instantly, is checked for corruption, and is combined when parts of a collection are merged, with deleted documents removed.
- Filtering is fast: in our tests on 1 million documents, a single condition takes between 2 and 80 microseconds and a combination of three conditions at most about 0.2 milliseconds, for stored and newly added documents alike.
- Searches can be filtered by fields of the stored JSON payload: equal to a value, one of several values, within a numeric range, or present at all, combined with and, or and not. Fields are declared when a collection is created (text, whole numbers, decimal numbers or true/false, also nested such as "meta.lang"), lists in a payload match when any element matches, and filters can be written as JSON. Filters work the same in vector, text and hybrid searches, and you still get as many results as you asked for whenever that many documents match.
- Vector searches with a filter that matches only a few thousand documents now check exactly those documents, which is faster than walking the vector index and always finds the true nearest matches.
- Fixed: with "fsync every 10 ms" or "no fsync", a power cut during a background save could lose a document that was being replaced (both the old and the new version). Deletes are now never saved ahead of the write that caused them.
- Documents whose JSON payload is nested more than 100 levels deep, and vectors so large that similarity cannot be computed, are now rejected with a clear error. Previously such a document was accepted and then made the collection unusable, including after a restart.
- A collection with damaged files no longer stops the database or its other collections from opening; the problem is reported for that collection. If the write-ahead log is damaged in the middle (rather than just cut off by a crash), the collection refuses to open instead of silently dropping the writes after the damage.
- A failed compaction is reported once to whoever asked for it and no longer makes later saves fail or leaves partial files behind. An internal failure in background work now stops writes with a clear error instead of leaving callers waiting forever.
- Deleting a collection now also works on Windows while the collection is still in use (an open handle or a running search). Its name can be reused immediately, and its files are removed as soon as nothing uses them any more, or when the database is next opened.
- Keyword search is up to three times as fast as before. On the MS MARCO benchmark (one million web passages), one processor core now answers about 2,400 searches per second when common words such as "the" are kept (previously 770) and about 3,000 with the English settings that skip them (previously 1,800), which is faster than tantivy, a popular search library, measured on the same machine (1,300 and 1,900). Slow searches improved most: 99% of searches now finish within 1.9 ms (previously 7.6 ms). The results are exactly the same as before.
- Text indexes are saved in a new format that is quicker to read. Indexes saved by earlier versions still open and give the same results; combining (compacting) them writes the new format.
